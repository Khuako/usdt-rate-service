# USDT Rate Service

gRPC-сервис для расчёта курса USDT/USD по стакану Kraken. Каждый успешный вызов `GetRates` получает свежий стакан, рассчитывает ask и bid, сохраняет результат и событие outbox одной транзакцией в PostgreSQL и возвращает курс клиенту. Отправка события в Kafka включается отдельно и выполняется в фоне.

Используется `GET /0/public/Depth?pair=USDTUSD&count=100`. Цены обрабатываются через `shopspring/decimal` и передаются в API строками. Объёмы заявок в расчётах не участвуют.

## Запуск через Docker Compose

Нужны Docker с Compose v2 и Make. Команды выполняются из корня репозитория. Для проверки API дополнительно нужен `grpcurl`.

1. Создайте `.env` в корне проекта:

   ```dotenv
   POSTGRES_PASSWORD=replace_with_your_local_password
   KAFKA_BROKERS=
   ```

   Замените значение своим паролем. Текущий Compose подставляет его непосредственно в URL подключения: используйте для локального запуска буквы, цифры, `_` и `-`. Пароли с зарезервированными символами URL требуют отдельного кодирования для строки подключения. `.env` исключён из Git и контекста Docker-сборки.

2. Запустите сервисы:

   ```bash
   make up
   docker compose ps -a
   ```

   Compose запускает PostgreSQL, ждёт его готовности, применяет миграции и запускает приложение. Jaeger запускается отдельным сервисом. Ожидаемые состояния: PostgreSQL — `healthy`, `migrate` — `Exited (0)`, `server` и `jaeger` — `Up`.

3. Проверьте API по примерам ниже.

Доступные адреса:

| Сервис | Адрес на хосте |
| --- | --- |
| gRPC | `localhost:50051` без TLS |
| Jaeger UI | http://localhost:16686 |

PostgreSQL и OTLP-порт Jaeger не опубликованы на хосте. Внутри Compose приложение использует `postgres:5432` и `jaeger:4317`.

Просмотр логов и остановка:

```bash
make logs
make down
```

`make down` сохраняет volume с данными PostgreSQL. Пароль БД задаётся при первой инициализации volume: изменение `.env` не меняет пароль уже существующего пользователя. Трассы Jaeger хранятся в памяти и не сохраняются при пересоздании его контейнера.

## API и расчёты

Контракт находится в [proto/rates.proto](proto/rates.proto). Метод: `rates.RatesService/GetRates`.

Позиции начинаются с **1**. Ask и bid рассчитываются независимо, в порядке уровней, полученных от Kraken.

| Метод | Параметры | Расчёт |
| --- | --- | --- |
| `TOP_N` | `n >= 1` | Цена на позиции N; `m` не используется |
| `AVG_NM` | `1 <= n <= m` | Среднее арифметическое цен с N по M включительно |

Позиции должны существовать в полученном стакане. Среднее округляется до восьми знаков после запятой; при `n == m` возвращается исходная цена. Нули в конце строкового представления не дополняются.

### TOP_N

```bash
grpcurl -plaintext \
  -import-path proto \
  -proto rates.proto \
  -d '{"method":"TOP_N","n":2}' \
  localhost:50051 rates.RatesService/GetRates
```

### AVG_NM

```bash
grpcurl -plaintext \
  -import-path proto \
  -proto rates.proto \
  -d '{"method":"AVG_NM","n":2,"m":4}' \
  localhost:50051 rates.RatesService/GetRates
```

Если `grpcurl` установлен через Go, но отсутствует в `PATH`, вместо `grpcurl` используйте `"$(go env GOPATH)/bin/grpcurl"`.

Ответ содержит `rate` с полями `id` (UUID), `ask`, `bid` и `receivedAt`. Время фиксируется приложением после получения HTTP-ответа Kraken; это не timestamp отдельного уровня стакана. Ответ возвращается только после успешного сохранения в БД.

Проверить сохранённую строку можно, подставив UUID из ответа:

```bash
docker compose exec postgres psql -U rates -d rates \
  -c "SELECT * FROM rates WHERE id = 'UUID_ИЗ_ОТВЕТА';"
```

Ошибки параметров возвращаются как `InvalidArgument`, отмена контекста — `Canceled`, превышение срока — `DeadlineExceeded`. Остальные ошибки возвращаются как `Internal` без внутренних подробностей; исходная причина записывается в серверный лог.

## Kafka и outbox

Для отправки событий подготовьте внешний брокер Kafka. При пустом `KAFKA_BROKERS` Kafka-клиент и фоновый отправитель не запускаются, но события продолжают накапливаться в `outbox_events`.

Для включения отправки задайте в `.env` адреса брокеров через запятую, доступные из контейнера приложения. Например, если брокер подключён к той же Docker-сети и объявляет внутренний адрес `kafka:29092`:

```dotenv
KAFKA_BROKERS=kafka:29092
```

Подключите брокер к сети, доступной приложению. Все адреса, которые Kafka возвращает клиенту через `advertised.listeners`, тоже должны быть доступны из приложения. `localhost` внутри контейнера указывает на сам контейнер приложения. Для подключения используйте listener с протоколом PLAINTEXT.

Подготовьте топик `rates.calculated` на брокере, затем примените настройку:

```bash
make up
```

При локальном запуске Go-приложения с брокером на хосте:

```bash
KAFKA_BROKERS=localhost:9092 make run
```

Для отключения отправки очистите `KAFKA_BROKERS` и перезапустите приложение. Уже сохранённые события останутся в БД.

### Отправка события

Курс и outbox-запись сохраняются одной транзакцией. Ошибка вставки события откатывает и курс. gRPC-ответ не ждёт Kafka.

Фоновый обработчик проверяет outbox по тику раз в секунду: выбирает до 100 неопубликованных записей и последовательно отправляет их. Каждый проход получает контекст с таймаутом пять секунд; проходы не выполняются параллельно. Этот таймаут не гарантирует завершение отправки за пять секунд: для уже отправленного запроса Kafka-клиент может продолжать ждать подтверждения от брокера. После подтверждения отправки выставляется `published_at`. При ошибке проход прекращается, ошибка логируется, а неопубликованные записи остаются для следующей попытки. Недоступность Kafka сама по себе не останавливает gRPC-сервер.

Ключ Kafka-сообщения — строковый `RateID`. Значение — JSON события:

```json
{
  "event_id": "3923ad83-22d6-4460-8e4f-e6da9a61d28d",
  "type": "rate.calculated",
  "version": 1,
  "occurred_at": "2026-09-20T14:58:58.660000Z",
  "rate_id": "159b9e6f-38aa-4d0c-b35f-42c5975f498a",
  "pair": "USDT/USD",
  "ask": "0.99965",
  "bid": "0.99962",
  "received_at": "2026-09-20T14:58:58.654008Z",
  "method": "topN",
  "n": 2,
  "m": 0
}
```

`event_id` совпадает с ID outbox-записи и сохраняется при повторных попытках. `occurred_at` — время создания события, `received_at` — время получения стакана. Метод в событии — строка `topN` или `avgNM`; для `TOP_N` поле `m` равно нулю.

Возможны дубликаты: Kafka могла принять сообщение до сбоя приложения или ошибки обновления `published_at`. Потребитель должен распознавать повтор по `event_id`. Запускайте один экземпляр приложения с включённым отправителем. Записи выбираются в порядке UUID. Опубликованные события сохраняются в таблице outbox.

Проверить событие для конкретного ответа API:

```bash
docker compose exec postgres psql -U rates -d rates \
  -c "SELECT id, topic, payload, published_at FROM outbox_events WHERE message_key = 'UUID_ИЗ_ОТВЕТА';"
```

При отключённой отправке `published_at` остаётся `NULL`. Для проверки доставки нужен работающий брокер и потребитель: найдите сообщение с тем же `event_id` в топике и проверьте заполнение `published_at`.

## Логи, трассировка и healthcheck

Zap пишет JSON-логи запуска, остановки и gRPC-запросов. Лог запроса содержит метод, длительность, код ответа и `trace_id`, если в контексте есть валидный span. Длительность в JSON выражена в секундах.

В Jaeger выберите сервис `usdt-rate-service` или найдите трассу по `trace_id` из лога. Успешный `GetRates` содержит три span: gRPC-запрос, `kraken.GetOrderbook` и `repository.Save`. При ошибке получения стакана span сохранения отсутствует. Отправка трасс выполняется в фоне, поэтому они могут появляться с небольшой задержкой.

Реализован стандартный RPC `grpc.health.v1.Health/Check`. Он принимает имя `rates.RatesService` или пустую строку, проверяет доступность PostgreSQL с таймаутом в одну секунду и возвращает `SERVING` либо `NOT_SERVING`. Неизвестное имя сервиса возвращает `NotFound`. Проверка определяет готовность по доступности PostgreSQL. Для вызова через `grpcurl` передайте стандартный `health.proto`.

При SIGINT/SIGTERM сервер отмечает healthcheck как `NOT_SERVING`, ожидает завершения gRPC-запросов до пяти секунд, затем при необходимости останавливает их принудительно. Контекст отправителя outbox отменяется при получении сигнала. После остановки gRPC сервер ожидает завершения отправителя ещё до пяти секунд. Если отправитель продолжает ждать Kafka, сервер закрывает Kafka-клиент и дожидается выхода фоновой горутины. На завершение экспортёра трасс выделено ещё до пяти секунд. Эти интервалы не задают строгий общий предел времени остановки: закрытие клиентов также занимает время.

## Локальная разработка

Нужен Go 1.26.2 или новее. Для `make lint` дополнительно нужен `golangci-lint` v2; проект проверялся версией 2.13.2.

| Команда | Действие |
| --- | --- |
| `make build` | Собрать `bin/usdt-rate-server` |
| `make run` | Собрать и запустить сервер локально |
| `make test` | Запустить `go test ./...` |
| `make lint` | Запустить `golangci-lint run ./...` |
| `make docker-build` | Собрать образ `usdt-rate-service:local` |
| `make up` | Собрать и запустить Compose в фоне |
| `make down` | Остановить и удалить контейнеры Compose, сохранив volume БД |
| `make logs` | Следить за логами сервера Compose |

### Настройки приложения

Приоритет: флаг командной строки → переменная окружения → значение по умолчанию.

| Переменная | Флаг | Значение по умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | `-database-url` | Нет, обязательная настройка |
| `GRPC_ADDR` | `-grpc-addr` | `:50051` |
| `KRAKEN_BASE_URL` | `-kraken-base-url` | `https://api.kraken.com` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Нет | Управляется OTLP-экспортёром; задавайте явно |
| `KAFKA_BROKERS` | `-kafka-brokers` | Пустая строка: отправка отключена |

`POSTGRES_PASSWORD` используется Compose. Само Go-приложение читает готовый `DATABASE_URL` и не загружает `.env` автоматически. Настройки OTEL читает SDK.

Для локального запуска нужна доступная с хоста PostgreSQL с применёнными миграциями из `migrations/`. БД в текущем Compose доступна только контейнерам; `make run` сам не запускает БД и не применяет миграции.

```bash
export DATABASE_URL='postgres://USER:PASSWORD@127.0.0.1:5432/DBNAME?sslmode=disable'
export OTEL_EXPORTER_OTLP_ENDPOINT='http://127.0.0.1:4317'
make run
```

В этом примере PostgreSQL и OTLP-приёмник должны быть отдельно доступны на указанных портах. Перед локальным запуском освободите порт `50051`, если его занимает сервер Compose.

### Тесты

```bash
make test
```

Тесты HTTP-клиента используют локальные тестовые серверы и не обращаются к настоящему Kraken. Тест репозитория требует отдельной PostgreSQL с применёнными миграциями:

```bash
TEST_DATABASE_URL='postgres://USER:PASSWORD@127.0.0.1:5432/TEST_DB?sslmode=disable' \
  go test -count=1 -v ./internal/rates/repository
```

Без `TEST_DATABASE_URL` тесты репозиториев **пропускаются**. Проверяются сохранение курса и outbox-события, содержимое JSON, выборка неопубликованных событий с лимитом и отметка публикации. Тест outbox-репозитория создаёт отдельную схему с копией таблицы, поэтому пользователю тестовой БД нужно право создавать схемы. Тестовые записи и схема удаляются после проверки.

Табличный тест `PublishPending` использует подставные репозиторий и publisher. Он проверяет пустую очередь, отправку двух событий, ошибки чтения, отправки и отметки публикации. Проверяются порядок вызовов, топик, ключ, payload и ID событий.

```bash
go test -v ./internal/outbox
```
